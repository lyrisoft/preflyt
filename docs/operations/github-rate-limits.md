# GitHub API rate limits

All outbound GitHub provider requests (App verification/token issuance, OAuth exchange/revocation, installing-user access, repository inventory and discovery) pass through a common limiter. API replicas sharing `REDIS_URL` and `REDIS_CACHE_PREFIX` share atomic pacing and cooldowns. Scope is App authentication, installation ID, or hashed user-token authentication budget. Redis keys contain SHA-256 scope digests, never tokens or response bodies. Existing cache deployment namespace keeps separate Preflyt deployments isolated; deployments using the same GitHub credentials should intentionally share the namespace if they need one coordinated budget.

Requests are paced at one slot per 250 ms per budget. Queues above two seconds fail promptly with a structured 503: `code: GITHUB_RATE_LIMITED`, `retryAfterSeconds` and `retryAt`. Rate-limit 403/429 responses honor Retry-After seconds/date and primary `x-ratelimit-reset` when remaining is zero, with a one-second safety margin. Headerless secondary rate-limit messages and missing/invalid timing use a 60-second cooldown. A successful response consuming the final primary allowance also pauses following requests. Redis TIME establishes shared pacing/cooldowns; concurrent shorter cooldowns cannot shorten an existing pause. Already dispatched requests cannot be recalled.

Long upstream cooldowns return immediately rather than sleeping inside an HTTP request. A caller retries after the indicated time. GET requests retry 502/503/504 at most twice with exponential delay and jitter; write requests, OAuth code exchanges and ambiguous network failures are not automatically retried. Ordinary 401/403/404 access failures retain their existing semantics. Rate limits do not deactivate installations or deselect repositories. JSON retry timing is preserved through repository inventory/discovery; OAuth browser callbacks retain their existing generic error redirect.

If Redis is disabled/unavailable, conservative per-process pacing and cooldowns remain active; coordination across replicas is unavailable until Redis recovers. This is degraded protection, not a shared limiter guarantee. Cache health warnings use the existing secret-free logger. Redis outage must be monitored operationally.

Concurrent installation verification and repository inventory reads within one API process are coalesced. Completed authorization responses are not cached, so the next request still checks upstream access. Repository inventory retains its existing 30-second Redis cache. Profile content remains capped at 32 files; webhook processing and automatic assessments read local data and require no outbound GitHub calls. No conditional ETag cache, cross-process read coalescing, token-response cache or full remaining-budget dashboard is implemented in this slice.

No migration or new environment variable is required. Restart the API after deploying; future worker GitHub clients must use the same limiter. Tests cover timing/header classification, primary/secondary limits, safe bounded retries, write non-retry, permission distinction, final-budget exhaustion, local fallback, request coalescing and real Redis coordination across two service instances. Tests use unique Redis prefixes and delete only their exact keys, never flush databases.
