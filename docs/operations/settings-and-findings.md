# Settings and Findings

Application connections and feature switches are now provisioned in **Settings → Configuration** by Super Admin. Environment names below describe the legacy import contract; once stored, database values take precedence. See [deployment configuration](deployment-configuration.md). Infrastructure and execution trust controls remain deployment-managed.

Settings lives at Administration → Settings (`/organization-settings`). Owners can update the local workspace display name; Admins can view it. The linked GitHub organization remains authoritative for the organization switcher. Writes require the existing origin check and organization permission and record `organization.settings.updated` in the audit history. Notifications reuse existing account preferences. Appearance reuses the browser theme preference. Organization model credentials and access management remain in their existing administration pages. The Configuration tab lets Super Admin manage deployment connections and capability switches, including before a workspace is selected.

Findings lives at Workspace → Findings (`/findings`). `GET /findings` requires assessment read permission and applies the caller's repository grants. The Reported issues tab combines failed saved checks and SARIF/JUnit issues from reports associated with the saved assessment. Evidence gaps shows incomplete checks. Filters cover repository, severity and search; pagination returns 50 results.

Every item includes the repository, exact source commit and a link to the saved assessment. Assessment digests, report checksums, delivery identity, repository and installation scope are checked before report details are exposed. Reported findings retain source-verification labels: an admin-associated report is not independent proof of tool execution. Source-report suppressions do not waive a policy. Credential-like report messages are omitted. HTML/logs are never rendered; absolute paths, URI schemes and traversal paths are rejected.

The worklist uses the latest saved assessment per commit, rather than implying that historical issues are current or resolved. Collection is bounded at 200 assessments, 100 unique reports and 2,000 results. Limits and unavailable report detail produce a visible partial-results notice. Existing native receipts without detailed imported reports expose check outcomes, not invented file-level findings.

Verification: isolated database integration tests cover Settings role/origin checks and audited writes, Findings repository scope, invalid filters, missing evidence and corrupted assessment hashes. Report projection tests cover stable fingerprints, file evidence, nested failed tests, credential redaction, encoded traversal, checksum tampering and XML entities. Chromium tests cover the empty/error/detail states, unverified report labels, badge semantics and Settings read-only/save behavior.

## Findings metrics and charts

The Findings response includes server-calculated summary metrics before 50-row pagination. Repository authorization, severity and applied search filters apply to both issues and evidence gaps. The cards show reported issues, affected repositories, critical/high issues and evidence gaps; affected repositories can have either an issue or a gap. Source-suppressed entries remain in the list but are excluded from metrics and charts. Failed-check summaries and individual report findings are distinct entries, not a count of unique vulnerabilities.

The severity donut and check bar chart follow the active tab. Severity counts can be selected to filter the list. The top eight checks are shown individually and the remainder grouped as Other checks; accessible counts preserve full labels. Empty and partial results remain explicit. Historical commits are included; charts do not claim currently open or resolved issues. No AI suggestions are counted and no resolution trend is invented without lifecycle evidence. Collection bounds also apply to summary metrics.
